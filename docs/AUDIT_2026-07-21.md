## 2. P0 / P1 findings (release-blocking)

### P1-A · `sync_2026_catalog` lets any authenticated user overwrite the global schedule
- **File:** `supabase/migrations/202607160005_scoreable_entry_catalog.sql:11-81,147` (twin: `20260716154714`). Client call: `src/components/SeasonBallot.tsx:74`.
- `security definer` function granted to `authenticated`; the only gate is `if auth.uid() is null` (line 21). It upserts `teams` and `games`, and `on conflict (canonical_key) do update` (lines 68-74) **reassigns home_team_id/away_team_id/week/venue of any existing game**. Games and teams are **global, shared by all users**.
- **Impact:** Any signed-in user (or anyone with the anon key + a JWT) can POST a crafted catalog to this RPC and corrupt every user's schedule, standings, and scorecards. Cross-user data-integrity, no admin role exists to justify the grant.
- **Confidence:** High (source-confirmed). **Affects production:** Likely Yes. **Blocks publish:** Yes. **Blocks merge:** Yes.
- **Fix:** Gate on an allowlist/service-role, or move catalog seeding out of a client-callable RPC. Reproduction: call `rpc('sync_2026_catalog', {catalog:[{key:<existing>,home:'X',away:'Y'}]})` as any authed user.

### P1-B · `sync-cfbd-scores` fails open when `SYNC_SECRET` is unset
- **File:** `supabase/functions/sync-cfbd-scores/index.ts:20-23`. Already tracked in `KNOWN_ISSUES.md:P0`, `ARCHITECTURE.md`, `HANDOFF.md`, `DECISIONS.md`, `CHANGELOG.md`.
- `if (expectedSecret && header !== expectedSecret) return 401;` — if the env var is unset/empty, the check is skipped entirely. The function then runs with `SUPABASE_SERVICE_ROLE_KEY`, calls `lock_due_entries()`, and upserts `games`. Empty-string secret also fails open; comparison is not timing-safe.
- **Impact:** If the function is publicly reachable and the secret isn't set, anonymous callers trigger service-role writes + entry locking.
- **Confidence:** High (code). Whether currently exploitable depends on deployment (secret set? function public?) — **Blocked test:** live trigger, needs deploy config. **Blocks publish:** Yes. **Blocks merge:** Yes.
- **Fix:** `if (!expectedSecret) return 500;` then require match (fail closed).

### P1-C · Migration ledger conflict + drift — fresh apply fails, source-of-truth ambiguous
- **Files:** every descriptive `202607NN…` migration has a Lovable-generated UUID twin that re-creates the same objects with **bare** `create type/table/function` (no `if not exists`/`or replace`): `202607150001`↔`20260716154448`, `160001`↔`154523`, `160002`↔`154601`, `160004`↔`154639`, `160005`↔`154714`, `160006`↔`154733`, `170001+200001`↔`20260720175508`.
- Descriptive files sort **before** their UUID twins, so on a fresh `supabase db reset` / new preview / DR environment the second copy errors (`type "ballot_status" already exists`). Verified by content diff. The pairs have also **drifted**: the UUID foundation adds explicit `grant` statements the descriptive one lacks → which schema is authoritative is unclear.
- **Impact:** Repo cannot be cleanly applied to any new environment; preview branches and disaster recovery break; ambiguity about production's real grant state.
- **Confidence:** High (fresh-apply conflict verified by diff). **Affects current production:** No (already migrated incrementally). **Blocks publish:** No. **Blocks merge:** Yes — do not merge a repo that can't reconstruct its own DB.
- **Fix (do NOT delete applied migrations blindly):** Inspect Lovable's `supabase_migrations.schema_migrations` ledger, determine which set production recorded, keep exactly one authoritative set, reconcile the grant drift.

### P1-D · Deadline is not enforced on the write path (enforcement depends on scheduler timing)
- **Files:** `save_entry_draft` / `submit_entry` (`202607200001:21-152`, `202607160005:83-145`) perform **no deadline check**. Only `reopen_entry` checks it. `lock_due_entries` (`202607160006`) locks `submitted` rows but is only invoked from `sync-cfbd-scores`, whose schedule is **not defined in-repo** (`config.toml` has only `project_id`).
- The deadline **is** configured: `ballot_deadline = 2026-08-28 23:59:59-04` (`202607160005:7-9`). But between that instant and the next `lock_due_entries` run, a `submitted`/`draft` entry stays editable — via the RPCs and via direct PostgREST `UPDATE` (RLS policy `entry_cloud_persistence:15-17` allows `status in ('draft','submitted')` with no time gate). Draft entries are never auto-locked at all.
- **Impact:** Picks can change after the deadline (potentially after kickoff) until the scheduler catches up. Magnitude depends on unknown scheduler cadence.
- **Confidence:** High (code). **Blocks publish:** Yes (integrity of a projection contest). **Blocks merge:** Yes.
- **Fix:** Add `now() < ballot_deadline` check inside `save_entry_draft`/`submit_entry`; add a deadline predicate to the ballots UPDATE RLS policy; schedule `lock_due_entries` independently of score sync.

## 3. What is SOLID (verified, not blocking)

- **Locked-entry immutability — strong, multi-layered:** `validate_prediction` trigger raises on locked ballots (`foundation:122-146`); `prevent_locked_prediction_delete` (148-163); RLS restricts prediction writes to `status='draft'`; ballots UPDATE `USING status in ('draft','submitted')` blocks locked rows; `save/submit` use `on conflict … where status in ('draft','submitted')` so locked entries can't be overwritten or replaced. No path found to mutate a locked entry via UI, direct PostgREST, RPC, or replay. **Championship + regular-season lock together** (single `locked_payload` snapshot in `lock_due_entries:13`).
- **RLS cross-user / cross-group isolation — correct:** ballots/predictions are owner-only; groups gated by `is_group_member`; profiles exposed only to self/public/fellow-member; leaderboard served by `get_group_leaderboard` security-definer RPC that checks membership first and filters to the target group (client correctly calls the RPC at `Groups.tsx:61`, not the broken view). No self-promotion (no group_members UPDATE policy), ownership can't be orphaned.
- **Git history — clean:** 172 commits scanned; no service-role key, `CFBD_API_KEY`, or `SYNC_SECRET` value ever committed. Tracked `.env` holds only `VITE_` publishable Supabase values (anon key) — the expected Lovable pattern, not a leak.
- **Calc invariants tested & passing:** canonical cross-team game IDs, complementary probabilities, standings, Notre Dame/playoff selection, playoff gating on 4 champions, versioned payload parse/restore (22/22 vitest).

## 5. P3 findings (post-beta safe)

- Neutral-site game at exactly 50% is rejected by `submit_entry` (SQL picks home team for non-neutral, raises for neutral) while the client returns "undecided" — divergent logic, reachable only via direct RPC (`202607200001:131-137` vs `oddsmaker.ts:196-211`).
- `standings.ts` and `playoff.ts` independently reimplement win/loss counting — divergence risk (maintainability).
- Group invite codes: 32 bits of entropy (`gen_random_bytes(8)` truncated to 8 hex chars) + no rate limit on `join_private_group` — theoretical enumeration.
- `weekly_scorecards` treats a tie (equal scores) as an away-team win (`foundation:209`) — no real CFB impact.
- Empty migration file `20260716154614_0c90cefd` (0 lines).
- `group_leaderboard` **view** (`private_groups:104`) is functionally dead (security_invoker over own-only ballots returns zeros); harmless because the client uses the RPC — recommend removing to avoid a future footgun.
- Assorted a11y: unlabeled email/group/vegas inputs, NotFound missing `<main>`, sub-44px touch target, whitespace-only group name passes client validation.
- `tsconfig` strict mode off (`strictNullChecks:false`, `noImplicitAny:false`); modeling constants hardcoded (conference-strength weights, G6 seed = 12); Vegas win totals manual.
- dev-tool-only advisories (vite/esbuild/rollup/postcss/ajv) — not shipped to prod.

## 9. What is needed to complete the blocked portion of the audit

This audit covered everything reachable through code review, database/schema analysis, security inspection, dependency/secret scanning, and public read-only testing. The items below (same set VALIDATION.md marks "Not validated") remain **reasoned from code, not proven by running them**, because this session was unattended, read-only, with no test accounts or service credentials.

### Hard constraint (does not change with access)
The auditor cannot type passwords into login forms or complete a Google/Apple/email sign-in (standing safety rule). **The sign-in step must be performed by a human;** the auditor can drive every authenticated action *after* login (create/join group, invite, leaderboard, cross-session restore). Auth therefore does not block group/entry testing — it just means a person clicks "sign in," then hands off.

### Recommended setup (fastest path to full coverage)
A **staging Supabase project cloned from production** + **two pre-signed-in test accounts** lets the auditor finish essentially the entire blocked list in one **interactive** session, including the write/destructive and deadline tests that must not run against real user data. Without staging, the auditor can still complete #1, #2, #3, #6, #7 on the live app (normal-user actions) and settle the migration ledger from the #6 query, leaving only #4/#5 live-fire for a staging pass.
